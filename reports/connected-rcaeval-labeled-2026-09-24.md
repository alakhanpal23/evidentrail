# Connected log selection on labeled RCAEval RE3-SS cases

This opt-in probe uses seven [RCAEval Sock Shop code-fault cases](https://huggingface.co/datasets/phamquiluan/RCAEval) with a published `root_cause.txt` line that occurs exactly once in the corresponding `logs.parquet` message and service columns. It ingests all 596,494 log rows into one source-bound encrypted corpus per case. The query is the same generic task for every case: “Investigate service errors and failed requests.” The selector sees no fault label, root-cause line, service name, or incident time. Each arm has a 32 KiB raw-log output budget. The original [dataset card](https://huggingface.co/datasets/phamquiluan/RCAEval/blob/afeacb11bcc94dadfd1c8f483ee4377b2b8b614e/README.md) says eight RE3-SS cases have root-cause files; the eighth, `re3ss_front-end_f2_2`, is excluded because its published root-cause message is absent from that case's logs.

Every selected line, including those chosen by the model, resolves to its exact encrypted source record. The recent baseline is scored for the labeled line, but was not scored for service/template coverage. No arm hit the byte ceiling. Before the repeated-severity path, first-ID and severity selection each made 17 selector calls across seven cases. Neither reported candidate-pool or service-directory truncation, although intermediate pages pruned 360 candidate groups across cases. These counts show that service membership is too weak a proxy for useful log selection in this setting.

The version-5 parser recognizes complete Spring Boot log preambles and seven-field HTTP access lines. It groups variable trace IDs, threads, request latency, and response size without altering the original source bytes. In an exploratory before/after run on the same seven pinned corpora, total indexed groups fell from 379,858 to 353,222 (7.0%). The line and template recall did not improve in the measured deterministic arms. A tested attempt to add severity samples to sparse lexical results also missed the labeled template while increasing candidate truncation and selector calls; that retrieval change was removed.

A subsequent stage audit found all seven labeled groups in the corpus but none in the lexical candidate list. Each was a repeated severe group (569–782 occurrences). A bounded indexed search now offers the highest-repeat critical, error, and warning groups alongside lexical candidates when no group matches at least two thirds of a three-or-more-term task. A specific LogHub BGL query matched all six terms; leaving its lexical ordering intact preserved the prior 12/12 category coverage and off-label output counts. With the same generic query and output budget, the first-ID arm selected the labeled template in all seven RCAEval cases and the exact labeled line in three. Four labels were interior occurrences of a repeated group, while the output currently resolves only its first and last representatives; exact-line recall is therefore limited even when the right template is selected. The new path made 28 first-ID selector calls versus 17 before, and all seven cases reported candidate-pool truncation; output byte budgets did not truncate. The severity arm made 24 calls versus 17 before. This is a useful candidate-recall improvement, not evidence that repetition always indicates causal relevance.

One local-only Qwen2.5-Coder 7B run with Ollama configured for a 32K context used the actual ID-only selector on all seven cases. Its 28 selection calls took 370.7 seconds of total query time (median 63.9 seconds, maximum 68.8 seconds per case). It saw the labeled group on at least one page in all seven cases, but retained it in the final group page in only three. It returned the exact labeled line in one case and its parsed template in three, versus three and seven for first-ID selection. The model returned 130 lines, versus 149 for first-ID, under the same 32 KiB raw-log cap; none of the arms exhausted that cap. This model and prompt are not qualified as the connected default. These labels are a retrieval proxy, not a full account of answer usefulness or coding-agent repair success. No hosted model or downstream repair was evaluated on these seven cases.

A focused local Qwen3 14B challenger on `re3ss_carts_f1_2` also missed the labeled line and template, despite the labeled group reaching its final page. Its five selection calls took 138.7 seconds, versus 67.7 seconds for Qwen2.5-Coder 7B on that case. One case does not rank the models overall; this result gives no reason to promote the larger model without a full paired study.

An evaluation-only replay on the seven pinned cases tested whether reserving at most two of the final twelve group slots for the most repeated severe groups would recover model omissions. The replay reuses the exact request/ID-selection trace from one Qwen2.5-Coder 7B run, then changes only the final group IDs; it makes no additional model calls. In that paired run, the model found the labeled template in 4/7 cases and returned 154 lines, while the guarded replay found it in 7/7 and returned 156 lines. Exact labeled-line coverage rose from 1/7 to 3/7. The first-ID baseline also found 7/7 templates and 3/7 exact lines with 154 lines, so the replay does not outperform that baseline. The model run took 374.3 seconds for 28 selector calls; the replay's separately reported 0.6 seconds is only replay/index time and must not be interpreted as end-to-end latency. The guard displaced model-selected groups in three cases. This small, label-inspected corpus cannot establish whether those displaced groups were useful, and the root-service count is not an irrelevant-line label. The guard remains an experiment, not the product selector. It needs an independently labeled, held-out noisy corpus and downstream repair comparison before promotion.

An exploratory pager change now carries at most eight high-repeat severe groups across intermediate selector pages, alongside the existing rare-service representatives; the final selector can still reject every carried group. In a second seven-case Qwen2.5-Coder 7B run, the labeled group reached the final page in 7/7 cases rather than 6/7. Template recall rose from 3/7 to 4/7 and labeled-service coverage from 4/7 to 7/7; exact-line recall stayed 1/7. It returned 154 lines rather than 130, including 27 rather than 20 lines from the labeled service. Non-root-service lines also rose from 110 to 127; those lines are not labeled as irrelevant. The 28 model calls took 319.1 seconds versus 370.7 seconds in the first run, but one local timing pair is not a latency distribution or proof the pager sped up inference. The first-ID arm kept 7/7 template recall and returned five more lines than before. The pinned BGL 12-category proxy retained its prior hits and off-label counts, and the six-case synthetic graph fixture retained its required evidence and 33 irrelevant lines. This is candidate-reachability progress with a small model-recall gain and a clear output-noise tradeoff, not a qualified routing policy.

Reproduce with `python3 -m pip install pyarrow==21.0.0`, then `python3 scripts/eval-rcaeval-connected.py --labeled > /tmp/evidentrail-rcaeval-labeled.txt 2>&1` and `python3 scripts/score-rcaeval-connected-labeled.py /tmp/evidentrail-rcaeval-labeled.txt`. The harness pins the dataset revision and SHA-256 of the case index, seven Parquet files, and seven root-cause files. It checks the unique label match before evaluation, keeps raw telemetry in a temporary directory, and prints only counts and metadata.

This is a hard, ambiguous task: a generic query over full history gives the selector no incident time or specific symptom, and the published line is not a complete set of all useful lines. Template matching is a second proxy, not a repair outcome. To reproduce the local model arm and its paired replay, start Ollama with `OLLAMA_CONTEXT_LENGTH=32768`, set `EVIDENTRAIL_COMPACT_LOCAL_MODEL=qwen2.5-coder:7b`, and add `--model` to the command above. The model and corpus revision should be held fixed for comparisons. Matched-budget downstream coding-agent fixes and live provider operation remain unqualified.
